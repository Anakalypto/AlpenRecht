Technical report: Alpenrecht AI

  • Track: Track 2B, own project: one legal question → every level of Swiss law
  • Event: Online
  • Team: RedPandas: Christopher Yazigi, Giovanni Yazbeck, Alfredo Pio Yazbeck
  • Demo: video (1:36) https://youtu.be/cG-jVfxx4d8 · web app via make run (http://localhost:5055); CLI make ask; screenshots in docs/

1. Summary

In Switzerland the answer to “Must my dog be on a leash?” or “When does night-time quiet start?” depends on where you live. The rule can sit in federal law, in one of 26 cantonal legal systems or in the regulation of one of more than 2,000 communes, in four languages and on different websites. Alpenrecht AI takes a question and an address and returns one answer covering all three levels: it retrieves the federal (Fedlex), cantonal (LexFind) and communal (the commune's own website) rules live, adds leading court decisions (entscheidsuche.ch), and Apertus-v1.5-70B writes an answer per level with every claim cited to the official text and fact-checked three times before display. It answers in DE / FR / IT / RM / EN, as of any date for federal law, and remembers the last 6 messages of a chat.

On 100 held-out questions (49 communal), graded blind by AI agents (Claude) against reference answers, the evaluated version scores 1.39/3 against 1.38/3 for the original prototype, a tie within grading noise. Both give 46/100 usable answers. The evaluated version makes fewer factual errors (43 vs 53) and is preferred head-to-head 43–36, but cites the governing source less often (53 vs 58), and communal questions remain the hardest (0.90/3). This set also guided the last day's choice between versions, so it is not fully independent (§5 d). On the 100-question development benchmark used for tuning, 85/100 answers cite a gold source (67 at baseline), and cantonal retrieval rises from 11/32 to 29/32.

2. Architecture

question + place + date (+ the last 6 chat messages)
   │
   ├─ swisstopo ─────────── address → commune, BFS no., canton, official languages
   ├─ Apertus (planner) ─── standalone question, levels, SR numbers + articles, title / keyword terms per language
   ├─ Fedlex SPARQL ─────── acts in force → consolidation valid on <date> → articles + annexes (tariffs)
   ├─ LexFind API ───────── Apertus writes the queries, picks the acts, then the articles (26 cantons, one API)
   ├─ communal docs ─────── commune website crawl (2,142 communes) · TLex · readers for 6 large cities · uploads
   ├─ case law ──────────── entscheidsuche.ch: Apertus writes the queries, ≤ 2 leading cases (BGE) with headnotes
   ├─ ranking + filter ──── stemmed BM25 over articles, annexes and tariff tables; Apertus relevance filter
   └─ Apertus (answer) ──── per level, every claim cited [n] ──► 3 verification rounds ──► answer + sources (SSE)
  • Apertus steers, code looks up. Apertus names the likely acts and articles; the code fetches exactly those from the official source. An invented article number simply finds nothing.
  • Three verification rounds (verify.py, checks.py), each: deterministic checks (every [n] exists, every named article is a source, no prose citations, every CHF amount appears in a source); fetching articles the draft names or the verifier asks for; an Apertus fact-check that lists every claim with a verdict; a rewrite only when the round found something. The UI shows a “3× geprüft” badge with the counts.
  • Communal law without a central collection (communal.py, cities.py): BFS number → official website (a table of 2,142 communes built from Wikidata) → regulations page (navigation, sitemap, common CMS paths, embedded JSON lists, TLex) → Apertus picks the regulation and the articles. Readers cover Zürich, Geneva, Basel, Lausanne, Bern and Lugano. Scanned or garbled PDFs are transcribed by Apertus itself (image input, 8B model).
  • Figures: annexes and tariff tables (“Anhang”, “Annexe”, “Tarif”) are indexed as sources; for fee questions the tariff that belongs to the chosen regulation or federal act is loaded too.
  • Conversation memory: the planner sees the last HISTORY_MESSAGES (default 6) messages, so “and for cats?” is searched as the full question.
  • Cache only while answering: downloaded law texts and crawls are shared by the parallel steps of a question; cache/ is emptied as soon as no question is running (uploads are kept).
  • App: Flask streaming server-sent events to a single-page UI (five languages, light and dark, phones); citation chips show the supporting sentence of the article; a CLI answers in the terminal.
Start page: the three levels for the chosen placeAnswer (Chur): cited per level, 3× checked

Target architecture: (a) on-premise, or (c) sovereign Swiss cloud. The app is one Docker container (Flask, Python 3.13) that talks to any OpenAI-compatible Apertus endpoint set by LLM_BASE_URL: a canton's own vLLM server (on-premise) or the CSCS inference service in Lugano (Swiss cloud, Swiss jurisdiction and data residency). Full questions and answers go only to that endpoint; the public sources receive the place and search terms derived from the question, never the full question. Questions are not logged (the access log records only request paths and place look-ups). At runtime it reads public Swiss legal sources (Fedlex, LexFind, swisstopo, Wikidata for communes missing from data/communes.json, commune websites and TLex, entscheidsuche.ch), so it is not air-gapped; build time needs only PyPI. The browser UI loads swisstopo map tiles, Leaflet (cdnjs.cloudflare.com) and Google Fonts; Leaflet and the fonts can be self-hosted on-premise. An air-gapped deployment (b) would need a local mirror of those sources.

3. Use of Apertus

  • Models: swiss-ai/Apertus-v1.5-70B for planning, retrieval steering, answers and fact-checks; Apertus-v1.5-8B for reading scanned pages (≈ 20 s for a 24-page regulation). Both run on the CSCS OpenAI-compatible endpoint; LLM_NAME / LLM_BASE_URL / LLM_API_KEY follow the judges' convention; on a single-model server, set OCR_MODEL to the same value as LLM_NAME in .env. The product uses no other model.
  • Other models (evaluation only): AI agents (Claude, Anthropic) drafted the 100 held-out questions and their reference answers from the official sources (each item re-checked by a second agent), and graded the answers in §5 (b) and §5 (d). Claude is not open-weights; it was used offline only, is not part of the product, never sees user questions and is not needed for make run.
  • How it is used (prompting only, JSON where structure is needed, a tolerant parser, one re-ask when the planner or fact-checker returns an empty list, and retries on transient API errors):
    1. planner: language, a clarified standalone question, levels, SR numbers and articles, search terms;
    2. LexFind agent: act titles and wildcard stems, act choice from up to 25 candidates, article choice from headings (the same heading-based article choice is used for Fedlex);
    3. communal: regulation and article choice; OCR of scanned or garbled PDFs;
    4. case law: search queries and the choice of at most two leading decisions;
    5. relevance filter, then the answer writer (strict citation style, one section per level, next steps);
    6. fact-checker: every claim with a supported / unsupported verdict, missing sources, then a rewrite.
  • Prompts are in pipeline.py, lexfind_agent.py, communal.py, caselaw.py and verify.py; answers run at temperature 0.2, planning and checks at 0.
Example (benchmark T071, graded 3/3): “Ab wann gilt die Nachtruhe?” in 7000 Chur → “In Chur beginnt die Nachtruhe um 23.00 Uhr und dauert bis 07.00 Uhr [4]. An öffentlichen Ruhetagen sowie werktags zwischen 20.00 Uhr und 23.00 Uhr ist dem erhöhten Ruhebedürfnis der Bevölkerung Rechnung zu tragen [4].” [4] = Polizeigesetz der Stadt Chur, Art. 30, found on the city's website. 16 claims checked in three rounds.

4. Data

  • Live public sources only: Fedlex (SPARQL + HTML), LexFind (cantonal law of all 26 cantons), swisstopo (geocoding), the communes' own websites and TLex, entscheidsuche.ch (court decisions).
  • data/communes.json: commune → official website for 2,142 communes, built once from Wikidata (CC0); data/wikidata_raw.json is the raw SPARQL export it was built from, kept for provenance and not read at runtime.
  • Evaluation sets in eval/: 14 questions (first rounds); 100 questions with gold sources (68 federal, 32 cantonal; DE 46 / FR 30 / IT 15 / EN 9; 15 cantons; federal gold articles checked programmatically to exist on Fedlex, cantonal gold acts chosen automatically from LexFind title matches); 100 graded test questions; 21 communal questions, three sets of 10 random communes and 18 fee questions; 100 held-out questions with reference answers (questions_heldout100.json, heldout100_reference.json).
  • No personal data is stored: questions are not stored, the crawl and law-text cache is emptied after each question, and uploaded regulations stay local.

(c) Communal law and figures.

  • Communal benchmark: 19/21 questions in 8 communes find and cite the commune's own regulation, e.g. Chur's Polizeigesetz Art. 30 “Nachtruhe 23.00–07.00”. In the graded runs, the communal regulation was retrieved for 9/10 communal questions.
  • Random communes (eval/random10*.json): 2/10 cite the commune's regulation on a first random set before the crawler fixes (TLex, two-column PDFs, OCR, polite retries); the fixes were tuned on a second set (5/10 → 6/10); on a fresh third set, 6/10 cite a communal regulation, 4 of them the correct, readable one.
  • Fees (eval/FEES.md, 18 questions in 12 communes and federal fees): the short answer states an amount from a source in 17/18 in the full run, 18/18 after a targeted re-run of the one miss (6/18 before), e.g. Basel dog tax CHF 160, Lugano CHF 115, Zürich parking card Fr. 300, passport CHF 140 (OLDI annex 2), debt-collection extract CHF 17 (GebV SchKG 12a).
  • Robustness: 0 errors and 0 timeouts in the 100-question runs; right language 99/100.

(d) Held-out check (eval/questions_heldout100.json, eval/ACCURACY_heldout100.txt, per-question data in eval/heldout/): 100 new questions, separate from the development sets (49 communal, 12 cantonal, 39 federal; DE 46 / FR 34 / IT 12 / EN 8). The same original answers scored 1.51/3 then and 1.38/3 in the final pass, so single-pass AI grading varies by about ±0.1/3 here. The later commits 9eb4d52 and 3bef387 (fee tariffs and ordinances, CHF amount check, Lugano reader, conversation memory, cache clearing) were not measured on this set; the fee changes only on the 18 fee questions and a 20-question regression sample. The tuning-set figures in (a)–(c) overstate accuracy on new questions.

6. Limitations

  • Accuracy: on new questions about half of the answers are usable and about 4 in 10 contain a factual error, mostly from a neighbouring article or a misread figure. Legal information, not legal advice.
  • Answer time: about 100 s on average, because of the three verification rounds. On the held-out set the evaluated version took 99 s on average (median 96 s, 80% between 61 and 142 s, maximum 208 s; 15 answers in parallel on a shared endpoint), against 140 s for the original; the v2 development run averaged 121 s. The UI streams every step meanwhile. VERIFY_MODEL=swiss-ai/Apertus-v1.5-8B is a faster option (its accuracy was not measured).
  • Federal article choice is the main lever left: the right act is usually found, the governing article not always.
  • Communal coverage depends on the commune's website: JavaScript apps, bot blocking or no linked regulations page cannot be crawled; the app then asks for an upload.
  • Scope: cantonal law is the current version only; case law covers published BGE with an official headnote; article splitting of cantonal PDFs is heuristic.
  • Not tested: human grading on the held-out set, the later commits on the held-out set, and air-gapped operation.

7. Reproducibility

  • Hardware: any x86-64 machine with Docker; no GPU, because inference runs on the hosted CSCS Apertus endpoint (or your own vLLM).
  • make run (Docker, python:3.13-slim) starts the web app; make test runs the 11 offline tests (no network, no API); make ask Q="…" PLACE="…" answers in the terminal; make eval SET=eval/questions_heldout100.json re-runs a question set live.
  • python eval/bench.py --set questions100.json --tag … --workers 5 re-runs a benchmark live; eval/build_set100.py rebuilds and re-verifies the gold set.
  • Held-out scores, offline from the stored blind grades (in eval/heldout/): python score.py grades_blind.json blind_key.json original evaluated ../questions_heldout100.json (details in eval/heldout/README.md).
  • Seeds: none; answers run at temperature 0.2, planning and checks at 0. Retrieval is live and Apertus is not perfectly deterministic, so a re-run can differ slightly.
  • Commit: the held-out numbers were measured at c0c4e48; fdb96d8 has the same pipeline code in this layout. Stored runs keep their answers, sources and verification logs in eval/results/ (development) and eval/heldout/ (held-out, with the blind key and grades).

8. Next steps
